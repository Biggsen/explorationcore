# ExplorationCore Plugin --- v1 Specification

## 1. Purpose

`ExplorationCore` is a small Paper plugin that provides persistent,
server-side storage of individual player exploration discoveries.

The plugin is a **persistence layer only** in v1.

Existing exploration logic remains responsible for detecting
discoveries. That logic is generated by `electron/ceGenerator.ts` as
ConditionalEvents configuration. When a discovery event fires,
ConditionalEvents will call `ExplorationCore` with the exact discovery
identity known by the generator.

The plugin stores the discovery in a local SQLite database.

The database becomes the authoritative local record of:

> **Which exploration entities has each player discovered on this
> server?**

The existing EXPMETRIC system remains unchanged and continues to serve
its current logging/POC purposes.

------------------------------------------------------------------------

## 2. Goals

Version 1 must:

-   Persist every supported player discovery locally on the Minecraft
    server.
-   Store stable machine identifiers rather than relying on display
    names.
-   Explicitly distinguish Overworld and Nether discoveries.
-   Distinguish entity types even when their display names are
    identical.
-   Record the actual discovery time.
-   Prevent duplicate discovery records.
-   Be safe for ConditionalEvents to call repeatedly.
-   Operate independently of achievement counters and EXPMETRIC timing.
-   Require minimal changes to the existing exploration system.
-   Provide a clean data foundation for a later `/exploration` feature.

------------------------------------------------------------------------

## 3. Non-goals

Version 1 must **not** implement:

-   `/exploration`
-   written books
-   inventory GUIs
-   player-facing exploration output
-   Region Forge catalogue parsing
-   world/server completion percentages
-   total available discovery counts
-   MCSM integration
-   Exploration Network syncing
-   log importing
-   historical EXPMETRIC importing
-   join/leave storage
-   session or playtime tracking
-   achievement-counter storage
-   EXPMETRIC `type=state` storage
-   rewards
-   replacement of EXPMETRIC
-   discovery detection

These can be considered separately after persistence has been proven
reliable.

------------------------------------------------------------------------

## 4. Existing System

Exploration events are currently generated in:

``` text
electron/ceGenerator.ts
```

The generator produces ConditionalEvents YAML.

ConditionalEvents detects exploration events such as:

-   region discovery
-   village discovery
-   heart discovery
-   nerve discovery
-   structure discovery

The existing generated configuration also emits `[EXPMETRIC]` console
lines.

EXPMETRIC currently contains useful analytics information, but it is not
suitable as the new database contract because it loses important
information:

-   discovery IDs are not logged
-   world/dimension is not logged
-   `region=` contains a display name rather than a stable ID
-   display names can contain spaces
-   a region and its heart can share the same display name
-   Nether state counters can report the wrong counter
-   state messages are delayed snapshots rather than discovery events

The new persistence mechanism must therefore receive discovery
information **directly from the generated discovery event**, not by
parsing EXPMETRIC.

------------------------------------------------------------------------

## 5. Architecture

The existing discovery system remains intact.

``` text
Player discovers entity
        |
        v
ConditionalEvents discovery event
        |
        +----> ExplorationCore record command
        |            |
        |            v
        |        SQLite DB
        |
        +----> existing player messages
        +----> existing achievements
        +----> existing rewards/actions
        +----> existing EXPMETRIC output
```

ConditionalEvents remains the discovery detector.

ExplorationCore does not need to know how a region, village, heart,
nerve or structure was detected.

Its responsibility is simply:

> Receive a valid discovery identity and persist it once.

------------------------------------------------------------------------

## 6. Persistence Timing

Database persistence must be independent of existing action timing.

Some existing ConditionalEvents actions deliberately use waits so that
achievements, counters, player feedback and EXPMETRIC state snapshots
occur in the correct order.

Those waits are **not relevant to persistence**.

The generated ExplorationCore command is the first action of a discovery
event, placed immediately after the conditions that confirm the
discovery have passed.

It must not wait for:

-   achievement counters
-   EXPMETRIC state output
-   rewards
-   messages
-   delayed ConditionalEvents actions

Existing action ordering should otherwise remain unchanged.

A write that happens before the discovery is confirmed becomes a
permanent row. Version 1 has no correction command. Bad metadata is a
migration, described in section 17.

### Design rule

> A discovery is persisted when the discovery event occurs, not when a
> later counter confirms it.

------------------------------------------------------------------------

## 7. Supported Discovery Types

Version 1 supports:

``` text
region
village
heart
nerve
structure
```

The value should be stored as a stable lowercase identifier.

Before insert, trim `entity_type` and lowercase it. `Heart` and `heart`
are the same stored value. Any value outside the list above is rejected.

The database should not assume that all types have the same semantics.

------------------------------------------------------------------------

## 8. World / Dimension

Every discovery must explicitly identify its exploration world.

Initial supported values:

``` text
overworld
nether
```

These are exploration-dimension labels. They are not Minecraft world
folder names such as `world` or `world_nether`.

Before insert, trim `world` and lowercase it. `Overworld` and
`overworld` are the same stored value. Any other value is rejected.

SQLite text comparison is case-sensitive. Normalization happens before
the uniqueness check, so the two spellings cannot become two rows.

Do not infer this later from:

-   display names
-   entity IDs
-   achievement counters
-   EXPMETRIC
-   current player location during a later operation

`ceGenerator.ts` knows which world is being generated and should provide
it directly.

The schema should not make adding another world value later
unnecessarily difficult.

------------------------------------------------------------------------

## 9. Discovery Identity

Each discovery has two different names with different purposes.

### `entity_id`

Stable machine identity.

Examples:

``` text
sakonotur
heart_of_sakonotur
widecombe
ocean_ruin_37
```

This is the value used for uniqueness and programmatic lookup.

`entity_id` is a single command token: non-empty, and containing no
whitespace. It is stored exactly as supplied. Uniqueness is
case-sensitive, so the generator must emit one canonical spelling.
The generator's existing stable id is that id. A changed id is a
different discovery.

### `display_name`

Human-readable presentation metadata.

Examples:

``` text
Sakonotur
Widecombe
Ocean Ruin
Inner Core
```

Display names are **not identities**.

`display_name` is required. After the command encoding in section 13 is
decoded, the value must be non-blank. It is stored exactly as decoded,
including spaces and other Unicode characters.

For example:

``` text
entity_type = region
entity_id   = sakonotur
display_name = Sakonotur
```

and:

``` text
entity_type = heart
entity_id   = heart_of_sakonotur
display_name = Sakonotur
```

must be stored as two distinct discoveries.

------------------------------------------------------------------------

## 10. Player Identity

The plugin should store:

``` text
player_uuid
player_name
```

`player_uuid` is authoritative.

`player_name` is stored as useful metadata and represents the player's
name at the time the discovery is recorded.

The player argument is a name. ExplorationCore resolves it to the UUID
of a player who is online when the command runs. It does not accept a
UUID from generated configuration.

If that player is not online, the command writes nothing and logs the
refusal. It must not look up an offline player, and it must not invent
a UUID.

------------------------------------------------------------------------

## 11. Server Identity

The server name should be configured once in the plugin configuration
rather than passed with every discovery command.

Example:

``` yaml
server-name: Lowothra
```

Other installations would use:

``` yaml
server-name: Charidh
```

or:

``` yaml
server-name: Teledosi
```

Store this value with each discovery record.

`server-name` must be non-blank. While it is missing or blank, record
commands write nothing and log the configuration error. Rows already
stored keep the server value they were written with. Changing the
configuration later does not rewrite them.

The unique key omits `server` because one database file belongs to one
server. A later merge across servers must treat `server` as part of
identity.

This makes the database self-describing and leaves a straightforward
path for future MCSM/network ingestion.

------------------------------------------------------------------------

## 12. Difficulty

Retain the current exploration difficulty semantics:

``` text
0 = not applicable / unknown
1 = easy
2 = normal
3 = hard
4 = severe
5 = deadly
```

Currently meaningful difficulty values apply to normal region
discoveries.

Villages, hearts, nerves and structures normally use `0`.

Difficulty is discovery metadata. It must not be used as part of
discovery identity.

------------------------------------------------------------------------

## 13. Record Command

ConditionalEvents requires a console-callable command that records one
discovery.

Command:

``` text
explorationcore record <player> <world> <entity-type> <entity-id> <display-name> <difficulty>
```

Every argument is one token. `<display-name>` is the display name
encoded as UTF-8 base64url (RFC 4648 section 5) with the padding `=`
characters removed. The plugin restores padding if needed, decodes the
token as UTF-8, and stores that text. The generator and the plugin both
use this encoding.

Logical fields:

``` text
player       = verzion
world        = overworld
entity_type  = region
entity_id    = sakonotur
display_name = Sakonotur
difficulty   = 2
```

Command line:

``` text
explorationcore record verzion overworld region sakonotur U2Frb25vdHVy 2
```

`Sakonotur` encodes to `U2Frb25vdHVy`. `Inner Core` encodes to
`SW5uZXIgQ29yZQ`.

Quoted display names are not part of the contract. A raw display name
can contain spaces, quotes, `%` sequences that ConditionalEvents would
treat as placeholders, or characters that split a console command.
Those characters stay inside the encoded token. The stored value is the
decoded text, so `Inner Core` is persisted as `Inner Core`.

### Validation

The record command writes a row only when every check below passes.
A failed check logs a diagnostic and writes nothing. The same
containment rule as section 22 applies: a rejection must not propagate
an exception or interrupt the ConditionalEvents action sequence.

-   `server-name` is configured and non-blank.
-   `<player>` names a player who is online. The UUID comes from that
    online player.
-   `<world>`, after trim and lowercase, is `overworld` or `nether`.
-   `<entity-type>`, after trim and lowercase, is one of the supported
    discovery types.
-   `<entity-id>` is a non-empty token and contains no whitespace.
-   `<display-name>` decodes as base64url into a non-blank string.
-   `<difficulty>` is an integer from 0 through 5 inclusive.

------------------------------------------------------------------------

## 14. Command Access

The record command is an internal integration endpoint, not a player
feature.

Players require the permission `explorationcore.record` to run the
record subcommand. That permission defaults to false and is not an
operator permission. Operators therefore cannot run it.

The server console and the remote console are allowed by sender type.
On current Paper, a permission whose default is false is not granted to
the console. ConditionalEvents invokes the command as a console action.
A panel console that writes into the server process is that same sender.

Do not advertise the record command as a normal player command.

Diagnostic subcommands use a separate permission,
`explorationcore.status`, which may default to operators. That
permission does not grant `explorationcore.record`.

------------------------------------------------------------------------

## 15. SQLite Storage

Default database location:

``` text
plugins/ExplorationCore/exploration.db
```

SQLite is sufficient because the database is local to one Minecraft
server and the initial workload is small.

The plugin owns database creation and schema initialization.

No external database service is required.

### Build target

Build the plugin against the Paper API version that Lowothra runs, and
declare that version as `api-version` in `plugin.yml`.

Bundle `org.xerial:sqlite-jdbc` inside the plugin JAR, shaded and
relocated. The server does not install a separate SQLite library.

Version 1 assumes an empty database. There is no schema migration. If
the table shape changes during development, stop the server and delete
the database file so the plugin can create it again.

------------------------------------------------------------------------

## 16. Discovery Schema

Initial schema concept:

``` sql
CREATE TABLE discoveries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    player_uuid TEXT NOT NULL,
    player_name TEXT NOT NULL,

    server TEXT NOT NULL,
    world TEXT NOT NULL,

    entity_type TEXT NOT NULL,
    entity_id TEXT NOT NULL,

    display_name TEXT NOT NULL,
    difficulty INTEGER NOT NULL,

    discovered_at TEXT NOT NULL,

    UNIQUE (
        player_uuid,
        world,
        entity_type,
        entity_id
    )
);
```

The implementation may add indexes or technical columns where useful,
but should keep the v1 model simple.

### Timestamp

`discovered_at` is generated by ExplorationCore when the record command
is handled.

Use one consistent, unambiguous representation.

Use UTC ISO-8601 with second precision and a `Z` suffix, for example:

``` text
2026-09-26T17:31:42Z
```

This will simplify future ingestion and comparison across servers.

------------------------------------------------------------------------

## 17. Idempotency and Duplicate Protection

Recording the same discovery more than once must be safe.

Uniqueness is defined by:

``` text
player_uuid
world
entity_type
entity_id
```

Example:

``` text
verzion + overworld + region + sakonotur
```

can exist only once.

A discovery row is immutable after insert.

If ConditionalEvents attempts to record it again:

-   do not create another row
-   do not change any column on the existing row, including
    `discovered_at`, `player_name`, `display_name`, `difficulty`, and
    `server`
-   do not treat it as a fatal error
-   do not generate noisy stack traces

If the generator supplied bad metadata, correcting it is a migration.
A later discovery event must not silently rewrite the historical row.

The command may optionally report a debug-level result such as:

``` text
Already recorded: verzion / overworld / region / sakonotur
```

but normal duplicate attempts should be harmless.

SQLite should enforce the uniqueness constraint in addition to any
application-level checks.

------------------------------------------------------------------------

## 18. State Is Derived, Not Stored

Do not store EXPMETRIC `type=state` snapshots.

For example, do not create persisted fields such as:

``` text
regions_discovered = 21
hearts_discovered = 5
structures_found = 37
```

These values can be derived from individual discovery records.

Example conceptually:

``` sql
SELECT COUNT(*)
FROM discoveries
WHERE player_uuid = ?
  AND world = 'overworld'
  AND entity_type = 'region';
```

The individual discovery ledger is the source of truth.

This avoids duplicating state and avoids inheriting the known Nether
counter mismatches from the current EXPMETRIC snapshots.

------------------------------------------------------------------------

## 19. Join and Leave Events

Do not store EXPMETRIC:

``` text
type=join
type=leave
```

in ExplorationCore v1.

They are useful for MCSM/session analytics but are not part of the
player's exploration record.

If session tracking is required later, it should be designed separately
rather than expanding the discovery schema prematurely.

------------------------------------------------------------------------

## 20. `ceGenerator.ts` Changes

The generator should add an ExplorationCore record action to every
generated discovery event that represents one of the supported discovery
types.

The generator already knows information that EXPMETRIC currently
discards:

``` text
world
entity type
entity ID
display name
difficulty
structure type, for structures
```

That information should be supplied directly to ExplorationCore.
Structure family is specified in section 30.
The display name in the generated command uses the encoding in
section 13.

Place that command as the first action after the event's discovery
conditions have passed, ahead of waits, messages, achievements,
rewards, and EXPMETRIC actions.

### Important

Do not generate the database command from the EXPMETRIC string.

Do not parse EXPMETRIC to recover discovery information.

Both outputs should be generated independently from the same source
discovery definition.

Conceptually:

``` text
Discovery definition
      |
      +---- generate ExplorationCore record action
      |
      +---- generate existing gameplay actions
      |
      +---- generate existing EXPMETRIC actions
```

------------------------------------------------------------------------

## 21. Existing EXPMETRIC Behaviour

Version 1 must not intentionally change existing EXPMETRIC output.

Existing:

``` text
type=discovery
type=state
type=join
type=leave
```

behaviour should continue as before.

This allows MCSM's current POC importer and Exploration Network to
continue working while ExplorationCore is introduced and validated.

The new database and EXPMETRIC therefore coexist initially.

------------------------------------------------------------------------

## 22. Failure Behaviour

A database problem must not break the player's exploration event.

A persistence failure must be contained within ExplorationCore. It must
not propagate an exception or otherwise interrupt the ConditionalEvents
action sequence. Bukkit's command result is not the contract: that
boolean only means the command was recognized, and ConditionalEvents
may never read it.

If persistence fails:

-   catch the failure inside the record handler
-   log a clear server-side error
-   include enough information to identify the failed discovery
-   do not crash the server
-   leave the rest of the ConditionalEvents action sequence running

A failed write should be visible to the server owner rather than
silently discarded.

Example diagnostic context:

``` text
player=verzion
world=overworld
entity_type=region
entity_id=sakonotur
```

Avoid logging excessive successful writes at INFO level during normal
operation.

------------------------------------------------------------------------

## 23. Plugin Lifecycle

On enable:

1.  Create the plugin data directory if necessary.
2.  Load configuration.
3.  Validate `server-name`. A missing or blank value is logged, and
    record commands refuse to write until it is set. Enabling still
    finishes so the misconfiguration is visible.
4.  Open/create the SQLite database.
5.  Create the schema if necessary.
6.  Register commands.
7.  Report successful initialization.

On disable:

1.  Cleanly close database resources.
2.  Do not modify discovery data.

The implementation should use safe resource handling and avoid leaving
SQLite connections/statements open unnecessarily.

------------------------------------------------------------------------

## 24. Configuration

Initial configuration can remain minimal.

Example:

``` yaml
server-name: Lowothra

database:
  file: exploration.db

debug: false
```

`database.file` may default to `exploration.db`.

A relative `database.file` resolves against the plugin data folder
(`plugins/ExplorationCore/`). An absolute path is used as given.

No database host, credentials or network configuration is required.

------------------------------------------------------------------------

## 25. Suggested Administrative Diagnostics

Not required for player functionality, but a minimal diagnostic command
would make rollout considerably easier.

Suggested:

``` text
/explorationcore status
```

Console/administrator output could include:

``` text
ExplorationCore
Server: Lowothra
Database: connected
Discoveries: 1432
```

Optionally:

``` text
/explorationcore player <player>
```

could report simple stored counts for validation.

These commands are administrative diagnostics only and must not evolve
into the future `/exploration` player UI during v1.

If keeping v1 absolutely minimal is preferred, `status` should be
implemented and `player` can be deferred.

------------------------------------------------------------------------

## 26. Logging

Normal startup:

``` text
[ExplorationCore] SQLite database ready
[ExplorationCore] Server identity: Lowothra
```

Successful individual discoveries should not need INFO logging by
default.

When `debug: true`, useful messages may include:

``` text
[ExplorationCore] Recorded verzion -> overworld/region/sakonotur
```

and:

``` text
[ExplorationCore] Duplicate ignored verzion -> overworld/region/sakonotur
```

Errors should always be logged.

------------------------------------------------------------------------

## 27. Acceptance Criteria

### A. Region discovery

Given a player named `verzion` discovers the Overworld region `sakonotur`:

The existing discovery experience must continue to work unchanged.

The database must contain one record equivalent to:

``` text
player_name  = verzion
world        = overworld
entity_type  = region
entity_id    = sakonotur
display_name = Sakonotur
difficulty   = appropriate region difficulty
discovered_at = actual discovery time
```

The player's UUID and configured server name must also be stored.

------------------------------------------------------------------------

### B. Duplicate region entry

If `verzion` later enters `sakonotur` again, the database must still
contain only one discovery record for:

``` text
verzion / overworld / region / sakonotur
```

The entire original row must remain unchanged, including
`discovered_at`, `player_name`, `display_name`, `difficulty`, and
`server`. A second command that carries a different display name or
difficulty must not rewrite those columns.

------------------------------------------------------------------------

### C. Region and heart name collision

If the player has:

``` text
region:
  entity_id = sakonotur
  display_name = Sakonotur
```

and later discovers:

``` text
heart:
  entity_id = heart_of_sakonotur
  display_name = Sakonotur
```

both records must exist independently.

------------------------------------------------------------------------

### D. Display name containing spaces

A discovery whose display name is `Inner Core` is passed on the command
line as the base64url token `SW5uZXIgQ29yZQ`.

The database must store:

``` text
Inner Core
```

The stored value is the decoded text. It must not be the token, and it
must not be truncated to `Inner`.

------------------------------------------------------------------------

### E. Nether discovery

A Nether region discovery must explicitly produce:

``` text
world = nether
```

It must not rely on the existing `%aach_custom_regions_discovered%` or
`%aach_custom_hearts_discovered%` state placeholders.

------------------------------------------------------------------------

### F. Structure discovery

A structure discovery must persist its individual structure identity,
not merely its family counter.

For example, two different ocean ruins must be capable of producing two
distinct records:

``` text
structure / ocean_ruin_37
structure / ocean_ruin_52
```

even if both have:

``` text
display_name = Ocean Ruin
```

------------------------------------------------------------------------

### G. Village discovery

A village discovery must persist as its own row:

``` text
world        = overworld
entity_type  = village
entity_id    = the village's stable id
display_name = the village's display name
difficulty   = 0
```

The row is distinct from any region, heart, nerve, or structure that
shares the display name or a similar id.

------------------------------------------------------------------------

### H. Nerve discovery

A nerve discovery must persist as its own row:

``` text
world        = overworld
entity_type  = nerve
entity_id    = the nerve's stable id
display_name = the nerve's display name
difficulty   = 0
```

The row is distinct from the parent region and from any heart that
shares the display name.

------------------------------------------------------------------------

### I. Rejected commands

The following write nothing and log a diagnostic:

-   an unknown world or entity type, including values that are not
    `overworld` or `nether` after lowercasing, and types outside the
    supported list
-   an empty entity id, or an entity id containing whitespace
-   a difficulty outside 0 through 5
-   a display-name token that does not decode to a non-blank string
-   a player who is not online
-   a blank `server-name`

`Overworld` and `overworld` are one stored world. `Region` and
`region` are one stored type. Recording both spellings of a pair must
leave a single row.

------------------------------------------------------------------------

### J. Restart persistence

After:

1.  recording discoveries
2.  stopping the Minecraft server
3.  starting it again

all discovery records must remain available.

------------------------------------------------------------------------

### K. Existing system regression

After installing ExplorationCore and replacing the generated
ConditionalEvents config:

-   discovery messages still work
-   achievements still increment
-   rewards/actions still work
-   existing waits still behave correctly
-   EXPMETRIC discovery output still works
-   EXPMETRIC state output still works

The persistence addition must not alter existing gameplay sequencing.

------------------------------------------------------------------------

## 28. Development and Testing Process

Development should be split into distinct stages so plugin/database
problems can be isolated from ConditionalEvents generator problems.

### Stage 1 --- Validate ExplorationCore independently

Use local Lowothra.

To reset local test data, stop the server and delete
`plugins/ExplorationCore/exploration.db`. The plugin creates a new
database on the next start. Leave the file in place while the server is
running.

1.  Build ExplorationCore against Lowothra's Paper API, with the SQLite
    driver bundled in the JAR.
2.  Install it without changing `ceGenerator.ts` or the existing
    ConditionalEvents configuration.
3.  Start the server and verify that the plugin creates its
    configuration and SQLite database.
4.  Run representative `explorationcore record` commands manually from
    the server console for a region, village, heart, nerve, and
    structure. Pass display names as base64url tokens.
5.  Inspect `exploration.db` and verify player UUID/name, server, world,
    entity type, entity ID, decoded display name, difficulty, and
    timestamp.
6.  Test a display name containing spaces, such as `Inner Core`, and
    confirm the stored text is `Inner Core`.
7.  Record the same discovery twice, the second time with a different
    display name and difficulty. Verify only one row exists and every
    original column is unchanged.
8.  Record a region and heart with the same display name but different
    IDs and verify both exist.
9.  Record a village and a nerve and verify each is its own row.
10. Test an explicit Nether discovery.
11. Reject an unknown world, an unknown type, an empty entity id, a
    difficulty outside 0 through 5, a bad display-name token, and an
    offline player name. Each attempt logs a diagnostic and writes no
    row.
12. Confirm an operator cannot run the record command, and the console
    can.
13. Restart the server and verify all records persist.
14. Confirm a database failure is logged and contained, and does not
    destabilise the server.

Do not modify the generated exploration configuration until this stage
passes.

``` text
manual record command
        ↓
ExplorationCore
        ↓
SQLite
```

### Stage 2 --- Integrate with ConditionalEvents

Only after Stage 1 passes:

1.  Add ExplorationCore command generation to `electron/ceGenerator.ts`.
2.  Generate a fresh Lowothra ConditionalEvents configuration.
3.  Inspect representative generated events for region, village, heart,
    nerve, structure, Nether region, and Nether heart.
4.  Verify each generated command contains the correct world, entity
    type, entity ID, display name, and difficulty.
5.  Verify the record command is the first action after the discovery
    conditions, and is not coupled to later waits or EXPMETRIC state
    timing.
6.  Replace the ConditionalEvents configuration on local Lowothra.
7.  Trigger real discoveries in-game.
8.  Verify all three paths independently:

``` text
ConditionalEvents discovery
        ├── existing gameplay behaviour
        ├── existing EXPMETRIC output
        └── ExplorationCore → SQLite
```

9.  Inspect `exploration.db`.
10. Re-enter already discovered entities and verify no duplicates are
    created.
11. Restart the server and verify persistence.
12. Confirm existing messages, achievements, rewards/actions, waits, and
    EXPMETRIC output still behave as before.

### Stage 3 --- Production rollout

Only after local end-to-end tests pass:

1.  Build the production plugin JAR.
2.  Generate the production ConditionalEvents configuration from the
    tested generator.
3.  Configure the correct `server-name`.
4.  Deploy the plugin and regenerated configuration.
5.  Restart/reload using the normal server deployment process.
6.  Verify plugin/database initialization in the server log.
7.  Verify at least one real discovery writes the expected database
    record.
8.  Retain the existing EXPMETRIC system during initial rollout.

Backfilling historical discoveries is a separate migration task and is
not required to validate v1 persistence.

------------------------------------------------------------------------

## 29. Future Direction

Once v1 has proven that discovery persistence is reliable, the database
can become the source for player-facing exploration functionality.

Likely next step:

``` text
/exploration
      |
      v
ExplorationCore
      |
      v
SQLite player discoveries
```

At that stage, Region Forge catalogue data can be introduced separately
to answer:

> What exists in this world?

Combining catalogue data with the player's discovery database would
allow:

-   per-type progress
-   region progress
-   structure progress
-   discovered/missing entities
-   completion percentages

Later still, MCSM may read or ingest these databases instead of
reconstructing exploration history from imported server logs.

The `/exploration` book, catalogue totals, and completion percentages
are specified separately. Storing `structure_type` on the row is
section 30, because structure progress cannot be counted from the
ledger without it.

------------------------------------------------------------------------

## 30. Structure type on the row

The book specification amends the record command. Six-argument
commands already installed keep working and store an empty
`structure_type`.

Structure discoveries gain one trailing token, the catalogue
`structureType`. The plugin stores it on the row and does not use it
as part of the unique key. A repeat of the same discovery must not
rewrite a family already stored. Regions, villages, hearts, and nerves
omit the argument.

The column is nullable. Adding it must not require deleting
`exploration.db`. Rows written before the column existed stay
unchanged until a separate backfill.

Family progress is a count of those stored values. It is not an
AdvancedAchievements counter, and it is not inferred from `entity_id`
or `display_name`.

## 31. Core Design Principle

The plugin should remain deliberately small.

**ConditionalEvents detects. ExplorationCore remembers.**

Everything else should be built on top of that boundary only when
needed.
