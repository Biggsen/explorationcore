# ExplorationCore Discovery & Progression Overhaul

**Status:** Draft for Cursor review  
**Version:** 0.1  
**Scope:** ExplorationMC (Charidh, Teledosi, Lowothra)  
**Objective:** Replace AdvancedAchievements (AACH) discovery/progression responsibilities, centralise discovery rewards and unlocks in ExplorationCore, substantially simplify ConditionalEvents (CE), and introduce a dedicated vanilla **Exploration** advancements tab.

> This is an implementation proposal, not an assertion about the current codebase. Cursor should inspect the repository, database schema, commands, CE configs and AACH configs, then challenge assumptions and propose revisions before implementation.

## 1. Current system and constraints

### 1.1 Existing responsibilities

- **WorldGuardEvents / ConditionalEvents:** detect entering named WorldGuard regions and invoke a sequence of console commands.
- **ExplorationCore:** records player discoveries in SQLite and exposes an `/exploration` book. Its database has reportedly already been backfilled with historical discoveries; **verify completeness and uniqueness before relying on it**.
- **AACH `Commands`:** per-discovery achievements (e.g. `discoverAuronia`), with some individual rewards.
- **AACH `Custom`:** counters and threshold-based achievements (e.g. `regions_discovered`, `total_discovered`, `structures_found`), with rewards, broadcasts and explorer-rank progression.
- **ExcellentCrates / crate plugin:** discovery crate keys, currently granted by CE.
- **LuckPerms:** book permissions and rank promotions, currently granted through CE/AACH commands.
- **Other integrations:** XP, claim blocks (e.g. `acb`), items, broadcasts, PlaceholderAPI, book display.

### 1.2 Representative current CE event

```yaml
auronia_discover_once:
  type: wgevents_region_enter
  one_time: true
  conditions:
    - '%region% == auronia'
  actions:
    default:
      - 'console_command: explorationcore record %player% overworld region auronia QXVyb25pYQ 1'
      - 'wait: 3'
      - 'console_command: aach give discoverAuronia %player%'
      - 'console_message: [EXPMETRIC] server=Charidh type=discovery entity=region player=%player% uuid=%player_uuid% region=Auronia diff=1'
      - 'console_command: cc give virtual RegionCrate 1 %player%'
      - 'console_command: lp user %player% permission set bookgui.book.auronia true'
      - 'wait: 6'
      - 'console_command: aach add 1 Custom.regions_discovered %player%'
      - 'wait: 6'
      - 'console_command: aach add 1 Custom.total_discovered %player%'
      - 'console_message: [EXPMETRIC] server=Charidh type=state entity=region player=%player% uuid=%player_uuid% total=%aach_custom_total_discovered% regions=%aach_custom_regions_discovered%'
```

**Desired end state:** CE detects the event and invokes **one** ExplorationCore command; ExplorationCore handles the rest.

```yaml
auronia_discover_once:
  type: wgevents_region_enter
  one_time: true
  conditions:
    - '%region% == auronia'
  actions:
    default:
      - 'console_command: explorationcore discover %player% overworld region auronia'
```

The final command signature is provisional. Prefer UUID-safe player resolution, and resolve name, display name and difficulty from an authoritative discovery registry rather than hardcoding encoded names in each CE event.

### 1.3 Non-negotiable invariants

1. **No duplicate rewards** from repeated events, restarts, retries, migrations or server reconnects.
2. **No lost discoveries** when an external reward plugin is unavailable.
3. **Historical backfill never automatically replays historical rewards.**
4. **No unintended change to existing player progress, permissions or explorer ranks.**
5. **First-write-wins** for unique discovery timestamps, consistent with current ExplorationCore behaviour.
6. **Per-server scope is explicit.** Charidh, Teledosi and Lowothra must not accidentally share discovery or milestone totals. Confirm current DB identity keys before changing anything.
7. **Backward compatibility during migration.** Existing `/exploration` book, `record` command, CE discovery detection and working rewards continue functioning until each responsibility is cut over.
8. **CE remains the discovery detector**, at least initially. Do not combine CE replacement with the reward-engine migration.

## 2. Target architecture

**Flow:** `WorldGuardEvents → ConditionalEvents → ExplorationCore discover → discovery ledger → milestone evaluator → reward/unlock dispatcher → book / placeholders / vanilla advancements`

### 2.1 Responsibilities inside ExplorationCore

- **Discovery registry:** valid discovery identifiers, world, category, display name, difficulty and optional overrides. Prefer reusing authoritative data already generated by Region Forge / MCSM; do not introduce a second manually maintained list without justification.
- **Discovery ledger:** authoritative unique player discoveries, including historical backfill.
- **Counters:** derived from unique ledger rows, not increment-only state. Support counts for region, village, heart, nerve, structure and total; inspect whether Overworld/Nether need distinct counters.
- **Milestone engine:** configurable thresholds and one-time completions, including explorer-rank thresholds.
- **Reward policies:** defaults per category/world, optional per-discovery overrides, and milestone-specific rewards.
- **Reward dispatcher:** XP, items, crate keys, permissions, claim blocks, console commands, rank promotions, notifications. Use native APIs where robust; otherwise adapters with validated commands.
- **Completion/reward journal:** persistent records for discovery and milestone reward status.
- **Presentation:** existing `/exploration` book, PlaceholderAPI values and a new vanilla Exploration advancement tab.
- **Administrative tooling:** dry-run simulation, inspection, reconciliation and retry diagnostics.

### 2.2 Separate definitions from policies

Avoid duplicating full reward definitions for hundreds of regions and structures.

Proposed conceptual configuration (illustrative; **not** final syntax):

```yaml
policies:
  overworld-region:
    on-first-discovery:
      - type: crate-key
        crate: RegionCrate
        amount: 1
      - type: permission
        node-template: 'bookgui.book.{id}'
        value: true

milestones:
  regions_discovered:
    source: discoveries
    filter: {type: region, world: overworld}
    thresholds:
      1: {rewards: []}
      15: {rewards: []}
      30: {rewards: []}
```

**Important:** These example thresholds show structure, not a complete import of the existing AACH configuration. Actual milestone counts, names and rewards must be extracted from the current `Commands` and `Custom` nodes. Do not silently replace existing rewards with examples.

### 2.3 Reward semantics and failure handling

- Record the discovery transactionally and generate deterministic completion/reward intents with stable IDs.
- Enforce unique constraints for discovery and milestone completion keys.
- Maintain statuses such as `pending`, `delivered`, `failed`, `suppressed_historical` (exact schema for Cursor to propose).
- External console commands cannot generally guarantee *exactly-once* delivery: a crash after command execution but before marking delivered can cause replay. Prefer idempotent operations (e.g. setting a permission) and plugin APIs with acknowledgement where available.
- **Do not blindly auto-retry non-idempotent rewards** such as crate keys, item grants or currency. Consider an `uncertain` state requiring inspection/manual reconciliation after ambiguous failures.
- Run Bukkit/Paper API interactions on the appropriate server thread. Keep database writes and scheduling safe for the existing plugin architecture.
- A reward failure must not roll back a valid discovery. It must remain observable and recoverable.

## 3. Incremental implementation plan

### Phase 0: Audit and baseline (recommended addition)

**Purpose:** Establish exactly what is being replaced before any behaviour changes.

**Work**
- Inventory ExplorationCore commands, services, SQLite schema, uniqueness rules, existing migration/backfill tooling and `/exploration` book.
- Parse AACH `Commands` and `Custom` configs for all three servers; catalogue per-discovery and milestone rewards, counters, announcements, permissions, XP and commands.
- Inventory CE event patterns and exceptions for regions, villages, hearts, nerves, structures and Nether content.
- Confirm `total_discovered` composition and whether thresholds differ by server; inspect `structures_found` versus any other structure counter.
- Audit non-discovery AACH functionality (e.g. votes) and decide whether it remains elsewhere or needs a separate replacement. **Do not uninstall AACH until all retained use cases are accounted for.**
- Take versioned backups of databases, CE/AACH configs, permissions and server plugin builds.
- Produce baseline test fixtures from anonymised/copied player records, including a near-milestone player and a fully progressed player.

**Exit criteria:** Documented responsibility matrix, current rewards/milestone catalogue, known exceptions, verified ledger completeness, rollback assets.

### Phase 1: Foundation in shadow mode

**Purpose:** Add infrastructure with **no live gameplay changes**.

**Work**
- Introduce registry/policy/milestone model and schema migrations.
- Implement derived counters, milestone evaluation and reward intent generation.
- Add a **shadow mode** that logs intended outcomes but does not mutate completion state or deliver rewards.
- Add `/explorationcore simulate <player> <type> <id>` (final syntax TBD): dry-run against a consistent snapshot, without writing to production tables, delivering rewards or granting advancements.
- Add diagnostic output for old/new counter and milestone comparison.
- Build test cases for duplicates, invalid IDs, cross-server isolation, out-of-order discovery dates and threshold crossings.

**Exit criteria:** Simulated outcomes match the existing AACH/CE rules for selected representative players; no new live rewards or permissions issued.

### Phase 2: Transfer individual discovery rewards, one category at a time

**Purpose:** Move crate keys, book permissions, individual XP/claim blocks and other per-discovery rewards into ExplorationCore.

**Work**
- Implement reward adapters and durable reward journal.
- Add **per-category feature flags**, preferably per server: `shadow`, `active`, `legacy` (exact model TBD).
- Pilot with **Overworld regions on a local test server**; expand only after proving one category end-to-end.
- Remove corresponding CE reward commands **only for the active category**; keep AACH achievement and counter commands temporarily if they are still needed.
- Explicitly suppress AACH `Commands` rewards for migrated categories to avoid double XP/claim blocks. Audit whether an AACH achievement grants anything automatically when `aach give` is called.
- Keep `record` semantics backward compatible; introduce `discover` for the new record/evaluate/reward workflow if that is the safest API.

**Exit criteria:** New discoveries grant exactly the existing rewards once, including across restart/re-entry; failed integrations are visible; legacy categories are unchanged.

### Phase 3: Replace AACH counters and milestones

**Purpose:** Transfer `Custom` discovery milestones, explorer ranks and associated rewards.

**Work**
- Derive counts from ledger queries; implement threshold crossing, persistent milestone completion and reward intents.
- Support thresholds crossed in a single operation and server-specific maximums.
- Map all AACH discovery counters, including `regions_discovered`, `villages_discovered`, `hearts_discovered`, `nerves_discovered`, `structures_found` and `total_discovered` where applicable.
- Preserve rank-promotion semantics; inspect whether LuckPerms `promote explorer` is safe to replay and whether direct group assignment would be safer.
- Replace `%aach_custom_*%` references with ExplorationCore PlaceholderAPI equivalents, including diagnostics and HUD where still used.
- Reconcile historical milestone completions with AACH data when available; otherwise establish a documented baseline policy from ledger counts and existing permissions/ranks. **Historical completion must not imply a new reward.**
- Switch each category's milestone authority only after parity checks; disable its old `aach add` commands at the same cutover.

**Exit criteria:** New thresholds fire once; existing players retain progress and ranks; counters match expected values; no double milestones.

### Phase 4: Dedicated vanilla Exploration advancements tab

**Purpose:** Add a compact, meaningful progression display separate from Minecraft's default advancements.

**Work**
- Design a root `Exploration` advancement with category branches for Regions, Villages, Hearts, Nerves, Structures and explorer ranks.
- Display **milestones**, not hundreds of individual discoveries; the `/exploration` book remains the detailed ledger.
- Evaluate datapack-defined advancement JSON plus Paper/Bukkit award APIs versus other supported mechanisms for the actual Minecraft/Paper version in use.
- Ensure root advancement, icons, descriptions, parent tree, criteria and visibility behave as intended. Decide whether advancement toast/chat announcements duplicate custom notifications.
- On first deployment/login, synchronise already-completed milestones to vanilla advancements **without replaying rewards**.
- Test player reconnect, server restart, world/server separation and future version upgrades.

**Exit criteria:** Exploration tab shows the correct milestone state for existing and new players and has no duplicate rewards or announcements.

### Phase 5: Simplify ConditionalEvents

**Purpose:** Reduce CE to discovery detection and a single ExplorationCore call.

**Work**
- Remove obsolete AACH commands, counter increments, crate grants, LP permissions, redundant waits and legacy metric lines once equivalent diagnostics exist.
- Generate or systematically transform CE discovery events from authoritative region/structure data, preserving detection conditions and `one_time` behaviour.
- Keep duplicate protection in ExplorationCore regardless of CE's `one_time: true`.
- Consider keeping `EXPMETRIC` temporarily behind a compatibility flag if other tools or reports still consume it.
- Validate every discovery category and representative exception against the baseline inventory.

**Exit criteria:** CE events are short, equivalent in behaviour, and can be regenerated consistently; ExplorationCore is the sole owner of discovery rewards and milestones.

### Phase 6: Retire AACH

**Purpose:** Remove AACH only after all retained functions are replaced or explicitly kept elsewhere.

**Work**
- Verify no live CE, scripts, HUD, placeholders, reward definitions or admin processes still depend on AACH.
- Account for non-discovery AACH achievements (notably votes if used); migrate, replace or explicitly accept their removal.
- Disable AACH on a copied test environment and run a complete discovery-to-milestone test.
- Promote through the existing **local test → promote → production** workflow, preferably one server at a time.
- Archive AACH databases and configs; retain a rollback runbook and reconciliation procedure.

**Exit criteria:** Servers function correctly without AACH; rewards, books, permissions, milestones, ranks, counters and advancements remain intact.

## 4. Suggested commands and observability

Names are provisional and should align with current ExplorationCore CLI conventions.

| Command | Purpose | Safety |
|---|---|---|
| `/explorationcore discover <player> <world> <type> <id>` | Real first-discovery workflow | Permission restricted; idempotent |
| `/explorationcore simulate <player> <world> <type> <id>` | Preview resulting discoveries, counters, milestones and rewards | **Strictly read-only** |
| `/explorationcore inspect <player>` | Display ledger counts, milestone state, pending/failed rewards | Read-only |
| `/explorationcore reconcile <player>` | Compare historical ledger and milestone state, report discrepancies | Dry-run by default |
| `/explorationcore rewards <player>` | Inspect reward journal | Read-only |
| `/explorationcore retry <reward-id>` | Operator-mediated retry for a known failed reward | Explicit permission, audited; avoid ambiguous deliveries |

Suggested log example (illustrative only):

```text
[ExplorationCore:SHADOW] server=Charidh player=<uuid> discovery=overworld/region/auronia new=true
[ExplorationCore:SHADOW] region_count=14->15 milestone=regions_discovered:15
[ExplorationCore:SHADOW] would_grant=[RegionCrate x1, bookgui.book.auronia, <configured milestone rewards>]
```

**Never use this sample as the source of actual Auronia milestone rewards.** Derive those from the live AACH configuration.

## 5. Data migration and cutover rules

The user's current understanding is that **all historical discovery rows have already been backfilled** into ExplorationCore. This should be verified, not repeated unnecessarily.

Distinguish three independent data classes:

1. **Discovery facts:** existing ledger rows, with original discovery timestamps.
2. **Milestone completion facts:** achievements already completed, potentially recoverable from AACH data or derivable as historical baselines.
3. **Reward delivery facts:** whether a crate key, item, command or permission was actually issued. These cannot always be reconstructed from discovery rows alone.

Recommended cutover:
- Preserve and back up current discovery data; do not rewrite historical timestamps.
- Seed historical milestone completion/suppression records without delivering rewards.
- Use a documented cutover timestamp or deployment generation **per server/category**; old rows are not eligible for newly enabled rewards.
- For existing players with missing historical rewards, provide a separate manual reconciliation policy rather than implicit mass backpay.
- Run old/new systems side by side only when exactly one is authorised to deliver each reward and milestone.
- If rollback occurs after new rewards have been issued, do not re-enable legacy reward paths without checking for duplication.

## 6. Test matrix

At minimum, test:

- First discovery, repeated CE event, repeated `discover` command, player reconnect, server restart.
- Existing backfilled discovery, including a player who has all regions discovered.
- A discovery crossing one milestone; one crossing multiple thresholds due to backfill/reconciliation.
- Failure or absence of crate plugin, LuckPerms, claim-block provider and item delivery.
- Crash/restart between discovery commit and reward dispatch; ambiguous reward execution.
- Permissions and ranks already granted; rewards partially delivered.
- Charidh/Teledosi/Lowothra isolation and world-specific counters.
- Overworld and Nether categories; structure-specific rewards and exceptions.
- PlaceholderAPI counter parity and removal of AACH placeholders.
- Advancements sync on first login, re-login and plugin/server reload.
- Full rollback using copied database and archived config.

## 7. Risks and open decisions for Cursor

1. **Existing schema:** What are the actual primary/unique keys, transaction boundaries and server identity semantics? Does the ledger reliably distinguish repeated discoveries?
2. **Backfill quality:** Are all discovery categories, worlds and players present? Can AACH historical completion data be mapped without guesswork?
3. **Reward APIs:** Which plugins expose stable Java APIs versus console-only commands? How will non-idempotent rewards be reconciled?
4. **Milestone parity:** What are the exact per-server AACH `Commands`/`Custom` definitions, including exceptions and non-discovery counters?
5. **Registry ownership:** Should MCSM/Region Forge export a shared discovery manifest, or should ExplorationCore load a generated registry from existing files?
6. **Cutover flags:** Per-server, per-world and/or per-category? How do flags interact with CE's one-time state?
7. **Advancement implementation:** How should vanilla advancement definitions be packaged, registered and kept compatible with the target Paper/Minecraft version?
8. **Reward recovery:** What states and manual tools are needed to avoid duplicate delivery after ambiguous external command execution?
9. **Cross-server scope:** Are ranks, milestones and discoveries independent by server today? Should any future network-wide achievements be explicitly separate?
10. **Scope boundaries:** Should non-discovery achievements such as votes remain outside ExplorationCore? Avoid turning it into a generic AACH clone.

**Guiding principle:** ExplorationCore becomes the single source of truth for exploration discovery and progression; CE only detects events; the `/exploration` book presents detailed discoveries; vanilla advancements celebrate major milestones. Preserve all existing rewards and player progress while making the transition reversible and observable.
